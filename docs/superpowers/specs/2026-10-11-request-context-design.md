# 번역 요청 문맥 확장 설계

번역 결과물 감사에서 용어 불일치 다음으로 많았던 문제는 요청 밖의 문맥이 필요한 경우였다. 한 요청은
번역할 블록들의 원문 전체를 문맥으로 받지만, 그 블록을 둘러싼 제목과 바로 앞뒤 블록은 보지 못한다.

- pypy `faq.rst`: 제목 "Is PyPy a drop in replacement for CPython?" 아래의 단독 블록 "Almost!"가 질문 없이
  "거의 다 됐습니다!"로 번역됐다(뜻은 "거의 그렇습니다").
- nix-dev: 목록 도입문 "This command does the following:" 다음 항목이 동작 설명이 아니라 독자에게 내리는
  명령("추가하지 마십시오")으로 번역됐다.
- pypy `rpython/doc/faq.rst`: 'The "No, don't!" above'가 앞 블록 답변을 앞 번역과 다른 말로 인용했다.
- 증분 번역에서 바뀐 문장 하나를 다시 번역할 때, 이웃 문장의 기존 번역을 보지 못해 용어와 어투가
  이웃과 어긋날 수 있다.

이 문서는 요청마다 읽기 전용 주변 문맥을 붙이는 방법을 정한다. 세그먼트, 해시, 상태 파일은 바꾸지
않으므로 이관할 것이 없다. 이미 번역된 세그먼트에는 영향이 없고, 앞으로 번역하거나 다시 번역하는
요청에만 적용된다.

## 1. 주변 문맥

요청(인접 블록을 묶은 배치)마다 다음을 만든다.

- **제목 경로.** 요청의 첫 블록이 속한 제목들을 바깥에서 안쪽 순서로 나열한다. 문서 순서로 블록을 보며
  제목 수준(`heading_level`, 없으면 1)으로 스택을 유지한다. 요청 자체가 제목이면 그 제목은 넣지 않는다.
- **앞 블록과 뒤 블록.** 요청에 들지 않은 번역 대상 블록 가운데 요청의 첫 블록 바로 앞의 것과 마지막
  블록 바로 뒤의 것. 목록 도입문, 코드 블록으로 끊긴 문장의 앞뒤, 질문과 답이 여기 들어온다.
- **기존 번역.** 제목과 앞뒤 블록의 세그먼트가 모두 번역되어 있으면 그 번역을 함께 보인다. 원문이
  바뀌어 번역이 낡은 세그먼트(`Stale`)의 번역은 보이지 않는다.

각 항목은 원문 300자, 번역 300자까지 자른다. 프롬프트에서는 번역할 문장 앞, 기존 문맥 뒤에 다음과
같이 둔다.

```
Where this text sits (for reference only; do not translate it):
Under headings: Is PyPy a drop in replacement for CPython? (translated as: …)
Before: <원문> (translated as: <번역>)
After: <원문>
```

지침 한 줄을 더한다. "주변 문맥은 지시어의 대상, 목록 항목의 문법, 질문에 대한 답, 이웃과 맞춰야 할
용어와 어투를 판단하는 데만 쓰고 번역하지 않는다."

인라인 태그 요청에서도 주변 문맥은 원문 그대로 보인다. 태그 번호가 번역할 문장의 태그와 섞이지 않게
하기 위해서다.

## 2. 요청의 용어집

요청은 지금까지 프로젝트 용어집 전체를 실었다. 용어 기준으로 항목이 수백 개가 되자(peps 600여 개)
요청마다 프롬프트가 크게 늘었다. 이제 요청의 세그먼트 원문에 실제로 나오는 항목(세그먼트 항목 포함,
`Glossary::find_matching_terms`)만 싣는다. 평가기는 지금처럼 용어집 전체로 판정한다.

## 3. 커스텀 프롬프트 템플릿

`prompt_template`에 `{surroundings}` 자리표시자를 더한다. 템플릿에 없으면 주변 문맥은 들어가지 않는다.
템플릿을 쓰는 프로젝트(raytracing, webassembly-component-docs)에는 `{context}` 다음에 넣는다.

## 4. 검증

- 요청 계획 테스트: 제목 경로, 앞뒤 블록, 기존 번역 표시, 낡은 번역 제외, 요청 용어집이 세그먼트에
  나오는 항목만 담는지.
- 실제 사례 재번역: pypy "Almost!"와 nix-dev 목록 항목을 비우고 다시 번역해 결과를 비교한다.
