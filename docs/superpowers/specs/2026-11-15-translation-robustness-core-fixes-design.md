# 번역 견고성 코어 수정 설계

MkDocs Material 사이트 *Linux Kernel Internals*(`parser = "mkdocs"`, `math = false`,
`definition_lists = true`, `inline_tags = true`, 5만여 세그먼트)를 번역하며 드러난 코어
결함 일곱 가지를 프로젝트 쪽 우회 없이 고친다. 각 절은 원인, 결정, 근거를 적는다.

공통 제약: 기존 프로젝트의 세그먼트와 state 상태(`status --check`의 출력과 종료 코드)는
바뀌지 않는다. 바꾸는 기본 동작은 3절(저장하지 않는 응답)과 5절(`evaluate`의 대상)뿐이고,
둘 다 이미 저장된 state를 건드리지 않는다.

## 1. 공백 없는 admonition 머리

### 원인

`scan_block_header`는 `!!!`·`???`·`???+`·`===` 뒤에 공백이나 탭이 있어야 머리로 읽는다.
Python-Markdown과 pymdownx의 정규식은 다음과 같아 admonition과 details는 공백이
선택이다.

| 확장 | 정규식 |
|---|---|
| `admonition` | `(?:^\|\n)!!! ?([\w\-]+(?: +[\w\-]+)*)(?: +"(.*?)")? *(?:\n\|$)` |
| `pymdownx.details` | `(?:^\|\n)\?{3}(\+)? ?(?:([\w\-]+(?: +[\w\-]+)*?)?(?: +"(.*?)")\|([\w\-]+(?: +[\w\-]+)*?)) *(?:\n\|$)` |
| `pymdownx.tabbed` | `(?:^\|\n)={3}(\+\|\+!\|!\+\|!)? +"(.*?)" *(?:\n\|$)` |

`!!!note`, `!!!tip "제목"`, `???info`, `???+warning "제목"`은 머리인데 파서는 머리와
본문(목록 포함)을 한 문단으로 읽었다.

### 결정

- 공백이 있는 꼴은 지금 규칙 그대로 읽는다(기존 세그먼트 불변).
- 공백이 없는 꼴은 `!!!`·`???`·`???+`에만, 정규식이 받는 범위만 머리로 읽는다
  (`is_unspaced_header_tail`): 표시 바로 뒤에 종류 낱말(`[\w-]+`, 공백으로 구분)이 오고,
  제목이 있으면 공백 뒤의 `"…"`가 줄 끝까지다. `!!!!`, `???what is this?`,
  `!!!"제목"`, `!!!note: …`는 글자다. `===`는 공백이 필수이므로 바뀌지 않는다.
- 그림자의 목록 표시는 머리 길이에 맞춘다: 7바이트 이상 `-   ***`, 5~6바이트 `- ***`,
  4바이트(`!!!a`) `-  -`(빈 중첩 항목을 담은 항목). 셋 다 4칸 들여쓴 본문을 항목의
  내용으로 읽게 한다.
- 재구성은 머리 줄을 원문 그대로 남긴다(공백을 넣지 않는다).

### 검증

공백 없는 머리를 쓴 쪽을 원문 그대로 읽은 세그먼트 목록이 공백을 넣은 사본의 것과 같다.
그래서 사본으로 번역한 state는 `reconcile`로 원문 쪽에 옮길 수 있다.

## 2. 직렬화 결과가 다시 읽히는 구조

### 원인

인라인 태그 직렬화기는 쓴 Markdown을 pulldown-cmark로 다시 읽어 태그 트리의 구조와
비교한다(`Renderer::score`). 두 구멍이 있었다.

1. **글자 대괄호를 막지 않는다.** 태그에서 나오지 않은 `]` 뒤에 `(`나 `[`가 붙으면
   링크가 되는데, 직렬화기는 강조의 표기만 바꿔 볼 뿐 대괄호는 그대로 쓴다. 다시
   읽기가 어긋나면 "확인하지 못함"으로 끝난다.
2. **다시 읽는 파서가 실제 렌더러보다 엄격하다.** `[59:56](top-byte ignore 영역)`은
   CommonMark에서 링크가 아니지만(목적지에 공백) Python-Markdown과 Pandoc은 링크로
   읽는다. 검증은 통과하고 사이트에서는 링크가 된다.

### 결정

불변식: **글자에서 나온 대괄호·느낌표는 계열의 어느 렌더러에서도 링크·참조·이미지·
각주·참조 정의를 이루지 않는다.** 쓰는 단계에서 만들고, 다 쓴 문자열에서 다시 확인한다.

**쓰기(`Renderer::escape`).** 글자 토큰의 문자를 쓸 때 다음을 역슬래시로 막는다.
`\]`·`\[`·`\!`는 CommonMark, Python-Markdown, Pandoc, MDX, MyST 모두 글자로 읽는다.

| 꼴 | 막는 글자 | 근거 |
|---|---|---|
| `]` 바로 뒤가 `(` | `]` | 인라인 링크. 목적지에 공백이 있어도 Python-Markdown·Pandoc은 링크 |
| `]` 바로 뒤가 `[` | `]` | 전체·축약 참조 `[a][b]`, `[a][]` |
| `]` 뒤 공백 하나, 그 뒤 `[` (`Dialect::MkDocs`) | `]` | Python-Markdown은 `[a] [b]`도 참조로 읽는다 |
| 줄 머리에서 열린 대괄호의 `]` 바로 뒤가 `:` | `]` | 참조·각주 정의 `[a]: …` |
| `[…]`의 글자가 문서가 정의한 참조 레이블 | `]` | 단축 참조 `[label]` |
| `[^…]` | `[` | 각주 참조. `]`를 막으면 역슬래시가 레이블에 들어간다 |
| 링크 글자 안의 글자 대괄호 | `[`와 `]` | 짝이 어긋나면 링크가 일찍 닫히거나 안쪽이 링크가 된다 |
| 토큰 끝의 `!` 바로 뒤가 `[` | `!` | `![…](…)` 이미지 |

- "바로 뒤"는 토큰 경계를 넘어 본다(`Renderer::first_char`). 글자 `]` 다음 토큰이 링크
  태그(`[`), 코드, 다른 글자 토큰이면 그 첫 글자가 기준이다. 단축·축약 참조 태그 뒤에
  `(`나 `[`가 올 때 전체 참조로 바꿔 쓰는 기존 규칙도 같은 판정을 쓴다.
- 링크가 될 수 없는 대괄호(`a[i]`, `[x] (y)`)는 막지 않는다.
- 원문이 대괄호를 역슬래시와 함께 쓴 세그먼트(`escape_brackets`)는 지금처럼 모든
  대괄호를 막는다.
- R Markdown은 `\[…\]`를 수식으로 읽으므로 `[`를 막아야 하는 꼴에서 `\[` 대신 문자
  참조 `&#91;`를 쓴다.

**확인(`Renderer::unsafe_closes`).** 글자가 막지 않고 쓴 `]`의 위치를 적어 두고, 다 쓴
문자열에서 그 뒤에 `(`·`[`(MkDocs는 공백 하나 뒤의 `[`도)가 오는지 센다. 0이 아니면 그
직렬화는 확인되지 않은 것이다(`Rendered::verified == false`). pulldown-cmark 다시
읽기와 별개로 돌므로 강조 표기를 바꾸는 전략이나 글자를 옮기는 변형이 새 인접을
만들어도 잡힌다.

**확인 실패의 설명.** `Rendered::mismatch`가 다시 읽은 구조와 태그가 뜻한 구조의 차이를
말로 낸다("원문에 없는 인라인 HTML", "링크 1개가 2개로 읽힘" 등). 3절의 재시도 피드백과
로그가 쓴다.

대상은 Markdown 계열 방언 전부(`CommonMark`, `Myst`, `Mdx`, `RMarkdown`, `MkDocs`)다.
XML 어휘(XHTML, CNXML, PreTeXt)는 직렬화기가 태그를 원문 그대로 되돌리므로 해당하지
않는다.

## 3. 깨진 태그가 든 번역

### 원인

- 응답의 `<b>`(번호 없는 여는 태그)는 태그 토큰이 아니어서 글자가 되고, MkDocs 방언은
  `<`를 막지 않으므로 날 HTML로 쓰였다.
- 직렬화가 확인되지 않아도 경고 issue만 달고 저장했다.
- `evaluate`의 태그 모드 검사는 산문 괄호뿐이고, `evaluate --audit`은 원문의 구조가
  번역에서 **줄었는지**만 본다. 번역에 **늘어난** 구조(태그 잔재가 인라인 HTML로
  읽히는 것, 글자 대괄호가 만든 링크)는 어느 검사에도 걸리지 않았다.

### 결정

**(a) 번역 시점.**

- 태그 문법으로 생겼지만 읽을 수 없는 조각(`<b>`, `<b/>`: 번호 없는 여는·빈 태그)은
  태그 문제다. 태그 글자에서 글자 `<`는 `&lt;`로 보이므로 날 `<글자>`는 모델이 쓴
  태그뿐이다. 단, `Position::Plain`(마크업 없는 문자열)과 원문 산문에 그 글자가 그대로
  있는 경우는 글자로 둔다.
- 확인되지 않은 직렬화는 태그 문제와 같은 길을 간다: 저장하지 않고, 무엇이 달랐는지
  (`Rendered::mismatch`)를 피드백으로 주어 그 세그먼트만 다시 요청한다.
- 최대 재시도 뒤에도 남으면 저장하지 않는다. 세그먼트는 Pending으로 남고 다음
  `translate` 실행이 다시 시도한다. "태그 글자는 번역으로 저장하지 않는다"는 기존
  `tag_problems` 관례와 같다. 앞선 시도에서 확인된 번역이 있으면(용어 검사에만 걸려
  재시도하던 경우) 그것이 남는다.
- 예외: 원문 자신의 태그 트리를 그대로 직렬화해도 확인되지 않는
  세그먼트(`source_verifies`가 거짓)는 직렬화기의 한계이지 응답의 결함이 아니다. 그런
  세그먼트는 지금처럼 경고 issue와 함께 저장한다(영원히 Pending으로 남아 배포를 막지
  않게 한다). 인라인 태그를 쓰는 기존 소스 전체(12만여 세그먼트)에서 그런 세그먼트는
  없다.

기본 동작의 변화: 지금까지 경고와 함께 저장되던 "확인되지 않은" 번역이 저장되지 않는다.
기존 state의 그런 번역은 그대로다.

**(b) `evaluate`.** 인라인 태그를 쓰는 소스의 파일에서 저장된 번역의 인라인 구조를
원문의 것과 비교하는 `InlineStructure` 검사를 더한다(`inline::audit::gained`).

- 원문을 태그로 읽을 수 있는 세그먼트만 본다.
- `structure()`(직렬화기의 다시 읽기)로 원문과 번역의 구조를 세어, 번역에 **더 많은**
  인라인 HTML·링크·이미지·각주 참조·MDX 표현식·Bikeshed 토큰을 ERROR로 낸다. 원문에 있는
  글자 `<b>`는 양쪽에서 같이 세이므로 오탐이 아니다. 강조는 세지 않는다(한국어 어순
  때문에 굵은 구절이 둘로 나뉘는 것은 허용이다).
- Python-Markdown·Pandoc으로 렌더링하는 방언(`MkDocs`, `RMarkdown`)에서는 글자 `](`도
  센다(`lax_inline_links`): CommonMark가 링크로 읽지 않는 `[59:56](top-byte ignore
  영역)` 꼴이다. `]`가 CommonMark가 읽은 링크·참조·각주 참조를 닫는 자리
  (`[글자][레이블](풀이)`, `[^1](…)`)는 그 구문의 것이므로 세지 않는다. CommonMark식
  렌더러를 쓰는 방언(`CommonMark`, `Myst`, `Mdx`)은 목적지에 공백이 있으면 링크가
  아니고, 링크라면 위의 링크 수에 잡히므로 따로 세지 않는다.
- 줄어든 구조는 `evaluate --audit`의 몫이다(고칠 수 있는지까지 본다).

## 4. 원문 그대로 남긴 구간 안의 용어

### 원인

용어 검사(`Glossary::unmet_terms`)는 원문에 용어가 산문으로 나오면 번역에 번역어를
요구한다. 면제는 외부 링크뿐인 세그먼트와 `except` 구절뿐이다. 번역하지 않는 제목
(`[mm: fix huge page accounting](url) — 설명`, `"The extensible scheduler class"`)
안의 용어는 번역어가 나올 수 없어 재시도가 수렴하지 않는다.

### 결정

**규칙.** 용어의 출현이 원문의 *구분된 구간* 안에 있고, 그 구간의 글자가 번역에 그대로
들어 있으면 그 출현은 충족된 것으로 본다. 용어의 모든 출현이 그렇게 충족되면 번역어를
요구하지 않는다.

- 구분된 구간(`delimited_spans`): 대괄호 짝의 안(Markdown·AsciiDoc의 링크 글자),
  큰따옴표 인용(`"…"`, `“…”`), 강조(`*…*`, `**…**`, `_…_`, `__…__`; 낱말 안의 `_`는
  강조가 아니다). 코드 스팬과 URL은 원래 용어를 찾지 않는다.
- 구간의 글자는 앞뒤 공백과 `,` `.` `;` `:`를 떼고 비교한다. 영어는 닫는 따옴표 안에
  쉼표를 두고(`"mm: fix …," the commit`) 한국어는 밖에 둔다.
- 괄호는 구분된 구간이 아니다. 괄호 안은 흔히 번역할 산문이고(`(top-byte ignore
  region)`), 통째로 영어로 둔 괄호를 면제하면 진짜 누락이 가려진다. 괄호 안의 약어
  풀이(`GIC (Generic Interrupt Controller)`)를 영어로 두는 프로젝트는 `except`를 쓴다.
- **구간은 용어보다 길어야 한다.** 구간의 글자가 용어 출현과 같으면(`**huge page**`,
  `"scheduler"`) 면제하지 않는다. 그 꼴은 용어를 영어로 둔 진짜 누락이고, 제목은 용어
  말고도 낱말이 있다. 기준은 "구간 안, 용어 출현 밖에 낱말 글자가 있다"이다.
- 비교는 대소문자를 가리지 않는다(용어 찾기와 같은 기준).
- 구간 밖에 출현이 하나라도 있으면 지금처럼 번역어를 요구한다.

**범위를 구분된 구간으로 한정하는 이유.** "원문의 아무 구절이나 번역에 그대로 있으면
면제"로 하면 용어를 영어로 둔 문장(`huge page를 할당합니다`)이 스스로 면제된다(원문의
`huge page`가 번역에 그대로 있으므로). 구분 기호가 있고 용어보다 긴 구간으로 한정하면
면제되는 것은 "여러 낱말짜리 링크 글자·인용·강조 구절을 통째로 옮기지 않은 경우"뿐이다.
그 구절을 옮기지 않은 것이 잘못이라면 그것은 용어 검사가 아니라 번역 범위의 문제이고,
용어 검사는 어차피 그 구절에 용어가 있을 때에만 우연히 잡았다.

**적용 자리.** `unmet_terms` 하나다(용어 평가와 `glossary adopt`가 같이 쓴다).
`find_matching_terms`와 스냅숏 판정(`is_snapshot_stale`)은 그대로이므로 기존 state의
상태는 바뀌지 않는다. 스냅숏에는 지금처럼 원문에 나온 용어가 모두 적힌다.

`except`는 남는다. 다른 뜻으로 쓰인 낱말(`in the future`, `entry points to`)을 빼는
본래 쓰임과, 구분 기호 없이 영어로 남기는 이름에 쓴다.

**효과.** *Linux Kernel Internals*의 `except` 259구절을 모두 지우고 저장된 번역을
평가하면 이 규칙 없이는 용어 위반이 339건, 규칙이 있으면 56건이다. 구절로 세면 259개
가운데 220개(84.9%)가 필요 없어진다. 남는 39개는 괄호 안의 약어 풀이, 영어로 둔 제목
세그먼트, 동사로 쓰인 낱말, 그리고 `except`가 가리고 있던 진짜 누락이다.

## 5. `evaluate`와 Glossary stale 세그먼트

### 원인

`evaluate`는 상태가 `Translated`인 세그먼트만 본다. 용어집을 바꾸면 영향을 받는
세그먼트가 `GlossaryStale`이 되어 평가에서 빠지므로, 어느 세그먼트가 새 용어집에
어긋나는지 나열할 방법이 없다.

### 결정

`evaluate`는 **현재 원문에 대한 번역이 저장된 세그먼트**를 모두 본다: `Translated`,
`GlossaryStale`, `ContextChanged`. `Pending`(번역 없음)과 `Stale`(원문이 바뀜)은 본다
해도 뜻이 없으므로 뺀다.

- 플래그가 아니라 기본 동작으로 둔다. `.github/scripts/`와 각 프로젝트의 `scripts/`는
  `evaluate`를 부르지 않고, CI가 통과한 state는 모든 세그먼트가 `Translated`라 결과가
  같다. 달라지는 것은 용어집을 바꾼 직후의 작업 트리뿐이며, 그때 보고 싶은 것이 바로
  이 목록이다.
- 평가는 언제나 현재 용어집으로 한다(스냅숏이 아니다). 로그 줄에 `status` 필드를
  더하고, 끝의 요약에 `Translated`가 아닌 세그먼트 수를 적는다.
- 정렬 검사(`Alignment`)도 같은 집합을 쓴다.

용어집 변경 뒤의 절차: `glossary adopt`(충족한 세그먼트의 스냅숏 갱신) →
`evaluate --mechanical-only`(남은 `GlossaryStale`의 위반 나열) → `translate`.

## 6. 영어 규칙 복수형

### 원인

용어는 낱말 경계에서만 맞으므로 `huge page`는 `huge pages`에 맞지 않는다. 프로젝트는
복수형을 따로 등록해야 했다.

### 결정

`[project] glossary_plurals = true`(기본값 `false`)이면 용어의 마지막 낱말에 영어 규칙
복수형을 붙인 꼴도 그 용어의 출현으로 읽는다.

| 용어의 끝 | 더 맞는 꼴 |
|---|---|
| ASCII 글자 | `…s` |
| `s`, `x`, `z`, `ch`, `sh`, `o` | `…es` |
| 자음 + `y` | `y` → `ies` |

- 출현의 범위는 복수형 접미사까지다. 그래서 4절의 "구간이 용어보다 길다" 판정에서
  `**huge pages**`는 용어와 같은 구간이다.
- 긴 용어가 먼저라는 규칙은 그대로다. `huge pages` 항목이 따로 있으면 그 항목이 맞고
  `huge page`는 그 자리에서 맞지 않는다(항목마다 번역어가 다를 수 있다).
- `except` 구절, `[whole]` 항목, 용어가 ASCII 글자로 끝나지 않는 경우(`C++`)는 바뀌지
  않는다. 불규칙 복수형(`indices`), 동사 굴절(`-ing`, `-ed`)은 다루지 않는다.

**옵션으로 두는 이유.** 복수형이 새로 맞으면 그 세그먼트의 스냅숏에 없는 용어가 생겨
`GlossaryStale`이 된다. 모든 프로젝트에 켜 보면 34개 가운데 33개에서 11,907개
세그먼트가 `GlossaryStale`이 되어 `status --check`가 실패하므로 기본값으로 켤 수 없다. 프로젝트 단위 옵션으로 두는 이유는 `glossary.toml`과
`terms.toml` 두 파일에 같이 적용되어야 하고, 항목마다 켜면 항목 수만큼 적어야 하기
때문이다.

켠 프로젝트는 복수형 항목을 지우고 `glossary adopt`로 스냅숏을 옮긴다. `terms build`는
원래 복수형을 단수형 후보에 접어 세고 정한 번역어를 두 꼴 모두에 항목으로 쓰는데, 켠
프로젝트에서는 규칙 복수형 꼴의 항목을 쓰지 않는다(`DecideOptions::plurals`).

## 7. 번역할 글자가 없는 세그먼트

### 원인

코드 스팬 하나뿐인 세그먼트나 `—`뿐인 세그먼트도 provider로 간다. 모델은 가끔 낱말을
보태거나 코드를 바꾸고, 그러면 평가·재시도가 돈다.

### 결정

번역이 필요한 세그먼트 가운데 **번역할 글자가 없는** 것은 provider를 부르지 않고 원문을
그대로 번역으로 기록한다(`translated_at`, 용어 스냅숏은 보통 세그먼트와 같게).

"번역할 글자가 없다"(`untranslatable::nothing_to_translate`)는 다음을 지운 나머지에
글자(`char::is_alphabetic`)가 하나도 없다는 뜻이다.

- 모든 마크업: 숫자, 문장부호, 기호, 공백은 원래 글자가 아니다.
- Markdown으로 읽는 마크업(`Markdown`, `MkDocs`, `MkDocsNoMath`, `RMarkdown`,
  `Bikeshed`)에서만: 백틱 코드 스팬, URL(`http://`, `https://`, `www.`), 링크·이미지의
  목적지(`](…)`), 숫자에 붙은 단위(`B`, `KB`·`MB`·`GB`·`TB`·`PB`, `KiB`·`MiB`·`GiB`·
  `TiB`·`PiB`, `Hz`·`kHz`·`MHz`·`GHz`, `ms`·`us`·`µs`·`ns`·`ps`).

보수적으로 정한 것:

- 다른 마크업에서 백틱은 코드가 아닐 수 있다(RST의 해석 텍스트·링크 글자, AsciiDoc의
  패스스루). 그래서 코드 스팬·URL·단위 규칙은 Markdown으로 읽는 마크업에만 쓴다.
  `myst`·`mdx` 파서도 `Markup::Markdown`을 알리지만, MyST 역할은 이름(`{ref}`)이, MDX
  표현식과 JSX는 그 글자가 백틱 밖에 있으므로 provider로 간다.
- 단위 목록은 한국어 문서가 그대로 쓰는 것만 든다. `s`, `min`, `h`, `m`은 "초", "분",
  "시간"으로 옮길 수 있으므로 넣지 않는다.
- 식별자·이름·버전 문자열(`foo_bar`, `v6.1`, `O(1)`, `Linus Torvalds`), HTML 태그와
  문자 참조(`<br>`, `&nbsp;`), 수식(`$x$`)은 글자가 있으므로 provider로 간다.
- 용어집이 그 세그먼트에 할 말이 있으면(`[whole]` 항목이거나 용어가 맞으면) 건너뛰지
  않는다.
- 번역이 없는 세그먼트(`Pending`)만 원문을 번역으로 받는다. 번역이 이미 저장되어 있고
  문맥 변화로 다시 번역할 차례가 된 세그먼트(`ContextChanged`)는 저장된 번역을 그대로
  두고 문맥 해시만 갱신한다. `Translated`인 세그먼트는 보지 않는다. 그래서 이미 저장된
  번역문은 바뀌지 않는다.

파일에 그런 세그먼트가 있으면 요청을 보내기 전에 state를 저장한다(보낼 블록이 하나도
남지 않을 수 있다). 요청에 남은 세그먼트가 없으면 요청 자체를 보내지 않고, 한 블록에
번역할 세그먼트와 섞여 있으면 번역할 것만 번호를 매겨 보낸다(문맥에는 그대로 보인다).
`plan_requests`도 같은 규칙으로 요청을 센다.

## 8. 검증

- 단위 테스트: 각 절의 재현 사례를 먼저 실패시키고 구현한다. 파이프라인은 가짜
  provider로 본다.
- `.github/pages-projects.json`의 모든 프로젝트에서, `rebuild-translations.sh`의 각
  분기가 쓰는 소스 인자로 `status --check`를 변경 전·후 바이너리로 돌려 출력과 종료
  코드가 같아야 한다.
- `mkdocs`·인라인 태그 프로젝트에서 `evaluate --mechanical-only`를 전후로 돌려 새
  보고를 진짜 결함과 오탐으로 나눈다.
- `cargo test --workspace`, `cargo clippy --workspace --all-targets`.
