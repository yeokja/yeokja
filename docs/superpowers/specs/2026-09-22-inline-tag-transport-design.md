# 인라인 태그 전송 설계 (1단계: Markdown)

번역 모델이 인라인 마크업의 문법을 직접 쓰는 구조를 바꾼다. 강조·링크 같은 인라인
구문은 번호 붙은 태그로 주고받고, 마크업 문법은 마크업별 직렬화기가 맡는다. 1단계는
mdBook으로 렌더링하는 `markdown` 파서 소스다. MyST·MDX, RST, 문단 단위 요청은 이후
단계로 둔다.

## 1. 배경

yeokja의 문서 모델은 블록 수준에서만 구조를 가진다. 파서는 문단·제목·목록 항목의
원문 바이트 범위(`Block.span`)를 기록하고, 재구성(`splice_reconstruct`)은 그 범위만
번역으로 바꾼다. 공백·주석·코드 블록은 범위 밖에 있어 바이트 그대로 남는다. 인라인
수준에는 구조가 없다. 문장 분할기가 나눈 원문 문자열(마크업 포함)을 그대로 모델에
주고, 모델이 돌려준 문자열을 그대로 끼운다.

그래서 한국어 조사가 마크업 규칙과 부딪히는 지점마다 모델이 문법을 스스로 판단해야
했고, 우리는 사후에 렌더러를 흉내 내는 검사와 보정을 마크업마다 덧붙였다
(translation-robustness 설계 문서 4·6·7·8절). 코드 스팬 내용 변경 86건, 역할의
리터럴화, 링크 목적지·단축 참조 손실, 조사 앞 AsciiDoc 제약 쌍, RST `\ `, CommonMark
강조 측면 규칙 88건이 모두 같은 뿌리다. `evaluator_format.rs`는 3,900줄이 되었다.

## 2. 조사 (스파이크, 2026-09-22)

같은 표본과 같은 채점으로 방향을 비교했다. 표본은 지난 강조 결함이 난 문단 전체와
rustc-dev-guide 세 챕터(`appendix/glossary.md`, `mir/index.md`,
`traits/goals-and-clauses.md`)로 서로 다른 세그먼트 680개다. 모델 호출은 yeokja와 같다
(`claude -p`, `claude-sonnet-5`). 채점은 최종 Markdown을 pulldown-cmark로 읽어 원문과
대조한다: 만들어진 강조 수, 글자로 남은 `*`·`_`, 코드 내용 다중집합, 링크 대상 다중집합.
조사 일치는 코드 스팬 바로 뒤 조사(을/를, 이/가, 은/는, 와/과, 으로/로)가 현재 번역과
같은 받침 쪽인지 보았다(대리 지표이며, 불일치는 손으로 읽어 판정했다).

| 방향 | 구조 결함 | 무효·누락 | 코드 뒤 조사 일치 |
|---|---|---|---|
| S0 지금 방식, 모델 출력 그대로 | 48 | 0 | 97% |
| S0 + 지금의 보정 | 25 | 0 | 97% |
| S0 실제 파이프라인(검사·재시도, 542개) | 3 | 0 | 100% |
| S1 태그, 코드 숨김 | 0 | 1 | 53% |
| S1 태그, 코드를 태그 안에 보임 | 0 | 1 | 91% |
| S1c 위 + 조사 규칙 | 0 | 0 | 92% |
| **S1b 태그, 코드는 백틱 그대로** | **0** | 3 | **98%** |
| S2 지금 방식 출력을 느슨하게 읽어 재직렬화 | 3 | 0 | 97% |
| S3 문단 단위 + 태그 | 0 | 8 | 95% |
| S3b 문단 단위 + 태그, 백틱 코드 | 0 | 17 | 96% |

- **표현은 무손실이다.** 모델 없이 태그로 바꿨다 되돌리는 왕복에서 CommonMark 8개
  프로젝트의 저장된 세그먼트 41,194개 가운데 41,190개가 렌더링 HTML까지 같았고
  99.4%는 바이트까지 같았다(나머지는 이스케이프 표기 차이).
- **모델이 쓰는 그대로면 13~14%가 깨진다.** 태그를 줘도 모델은
  `<b1>외적(outer product)</b1>에서`처럼 쓴다. S1b에서 97건이 이렇게 나왔고 직렬화기가
  모두 순수 Markdown으로 고쳤다(`_`→`*` 45, 괄호 풀이 밖으로 30, 조사 안으로 21,
  링크 안으로 4, 따옴표 밖으로 2).
- **코드 내용은 모델에게 보여야 한다.** 조사는 앞말의 받침을 따른다. 코드를 빈 태그로
  숨기면 조사가 동전 던지기가 되고(53%), `<c1>v</c1>`처럼 태그 안에 보여도 91%에
  그치며 `은(는)`처럼 얼버무린다. 백틱 그대로면 98%다.
- **모델의 태그 실수는 얕다.** 닫는 태그 번호 누락(`</i>`), 종류 글자 바꿈, 지어낸 빈
  태그, 코드 속 `Vec<i32>`, 한국어가 주어를 되풀이하며 코드나 강조를 두 번 쓰기가
  대부분이고, 느슨한 판독으로 받아들일 수 있다. 태그를 쪼개거나 합친 진짜 실패는
  1~2건이다.
- **S2**(출력 형식을 바꾸지 않고 사후 재직렬화)는 모델이 강조를 빠뜨리거나 코드를 고치는
  것을 막지 못한다. 기존 번역 감사·수선 도구로는 쓸모가 있다.
- **S3·S3b**(문단 단위)는 정렬 결함을 원천적으로 없애고 조사도 좋지만, 요청 형식과
  재시도 방식을 크게 바꾼다. 표시 누락은 한 줄짜리 용어 제목(`<span id>…`)에만 생겼다.
- **S4**(RST): docutils 기반 코덱으로 pypy·cpython-devguide·mil 전체와 peps 12,000개,
  23,263개를 왕복해 구조를 전부 지켰다(태그로 못 바꾼 8개는 문장 분할이 인라인 마크업을
  자른 곳). 모델 98개도 태그가 모두 유효했고 렌더러가 넣은 `\ ` 159개는 저장된 번역이
  직접 넣은 153개와 거의 같다. Rust 구현 비용은 Markdown의 2~3배로 본다.

**증거의 한계.** 변형마다 한 번씩 돌렸다(분산을 보지 않았다). 표본의 일부(190개)는 강조
결함이 났던 문단이라 태그 쪽에 유리하고, 나머지는 한 프로젝트·한 방언(mdBook)이다.
조사 일치는 저장된 번역(역시 모델 출력)과의 일치라 대리 지표다. 채점은 태그가 **엉뚱한
한국어 낱말**을 감싼 경우를 보지 못한다. S1b의 무효 3건은 재시도 전, S0 실제 파이프라인의
결함 3건은 재시도 후 수치라 같은 선상이 아니다(재시도 전끼리는 S0 48건 대 S1b 0건).
그래서 롤아웃의 합격 기준(4절)에 사람이 읽는 표본과 두 번의 실행, 재시도율을 넣는다.

부수 발견: claude_code provider가 사용자 설정을 읽어 플러그인 세션 훅이 번역 호출마다
실렸다. `--setting-sources local`로 고쳤다(`ffdd612`).

## 3. 결정

### 3.1 전송 형식

모델과는 태그 텍스트로 주고받고, state에는 지금처럼 완성된 Markdown을 저장한다.
state 형식, 재구성, 기존 번역은 바뀌지 않으므로 이행이 필요 없다.

| 원문 구문 | 태그 텍스트 | 되돌리기 |
|---|---|---|
| `*x*`, `_x_` | `<iN>x</iN>` | 직렬화기가 표기를 고름 |
| `**x**`, `__x__` | `<bN>x</bN>` | 〃 |
| `~~x~~` | `<sN>x</sN>` | 〃 |
| 링크 `[x](u)`, `[x][r]`, `[x]` | `<aN>x</aN>` | 원문의 꼬리(`](u)`, `][r]`)를 붙임 |
| 코드 `` `x` `` | `` `x` `` 그대로 | 원문 바이트로 되살림 |
| 짝이 맞는 인라인 HTML `<kbd>x</kbd>`, `<span id="a">x</span>` | `<hN>x</hN>` | 원문의 여는·닫는 태그 |
| 그 밖의 인라인 HTML, 이미지, 자동 링크, 각주 참조, 줄바꿈 | `<xN/>` | 원문 바이트 |
| mdBook MathJax `\\(…\\)`, `\\[…\\]` | `<mN/>` | 원문 바이트 |

- "원문 바이트"는 세그먼트의 원문 문자열(state의 `source`)을 말한다. 세그먼트는 문장
  분할기가 만든 문자열이라 문서 바이트 오프셋이 없다.
- 세그먼트 문자열을 태그화할 때 문서 수준 정보를 함께 쓴다: 참조 정의 레이블
  (`[r]: …`, 정의가 있어야 링크로 읽힌다)과 세그먼트가 속한 블록의 종류(표 셀인지).
  각주 참조 `[^x]`는 정의가 문서에 있으므로 언제나 불투명하게 둔다. 세그먼트 앞에 블록
  표시로 읽히는 글자(`1.`, `- `)가 있어도 인라인으로 읽는다.
- **태그화할 수 없는 세그먼트**: 원문 자체가 짝을 이루지 못한 `*`·`_`·백틱을 남기면
  (문장 분할이 강조나 코드 안에서 끊은 경우 등, robustness 7절의 "원문이 연 표시") 그
  세그먼트는 태그로 표현할 수 없다. 그런 세그먼트가 하나라도 든 요청은 통째로 기존 경로
  (원문 Markdown, 지금의 프롬프트·보정·평가기)로 보낸다. 스파이크 왕복에서 0.01% 미만이다.
- 번호는 요청 하나 안에서 유일하다. 요청의 문맥(`batch_block_groups`가 합친 블록들)에
  든 세그먼트는 번역 대상이 아니어도 모두 같은 번호 체계로 태그화하고, 프롬프트에 "문맥의
  태그는 참고용이며 번호 붙은 문장에만 답한다"고 적는다.
- 텍스트의 `<`, `>`, `&`는 `&lt;`, `&gt;`, `&amp;`로 준다. 응답에서는 이 세 가지만 되돌리고,
  그 밖의 엔티티처럼 보이는 글자는 글자 그대로 둔다(직렬화 때 필요하면 이스케이프한다).
- 이미지의 대체 텍스트는 1단계에서 번역하지 않는다(원문 바이트). 지금은 번역되므로,
  다시 번역되는 세그먼트에서는 의도한 후퇴다.

### 3.2 판독과 검증

모델 응답은 느슨하게 읽는다.

- 백틱 스팬을 먼저 떼어 내고, 그 뒤에 태그를 읽는다(`Vec<i32>`를 태그로 읽지 않는다).
- 번호가 태그의 정체다. 종류 글자가 틀리면 표의 종류로 고친다.
- 번호 없는 `</i>`는 가장 안쪽에 열린 `i`를 닫는다.
- 표에 없는 태그는 버린다.
- 코드 스팬은 **엄격하게** 원문 코드에 맞춘다. 응답의 스팬마다 차례로:
  1. 내용이 같은, 아직 맞추지 않은 원문 코드가 있으면 그것이다.
  2. robustness 4절이 허용하는 덜어 내기(영어 복수형, 산문에서 부를 때의 `()`, 스팬 끝의
     문장 부호·짝 없는 괄호)로 원문 코드를 설명할 수 있으면 그것이다
     (`stands_for`·`shed_edges`를 그대로 쓴다).
  3. 이미 맞춘 원문 코드와 같으면 되풀이다(한국어가 주어를 다시 부름).
  4. 내용이 세그먼트 원문에 평문으로 있으면 평문을 코드로 쓴 것이다(robustness 6절,
     `written_as_text`). 모델이 쓴 그대로 둔다.
  5. 어디에도 해당하지 않으면 문제다: "code `X` is not in the source (did it change?)".

  1~3에 맞춘 스팬은 원문 바이트로 되살린다. 끝까지 맞추지 못한 원문 코드가 남으면 역시
  문제다("code `X` is missing"). 순서만으로 맞추지 않는다: 모델이 `fold=0`을 `fold`로 바꾼
  것(robustness 4절의 결함)을 다른 원문 코드로 조용히 덮어쓰게 되기 때문이다.
- 강조·링크 태그는 한 번씩 나와야 한다. 단 강조는 두 번 나와도 된다: 원문이 한 구를
  굵게 했는데 한국어 어순이 그 구를 둘로 가르는 경우다(`<b1>X</b1>에서 <b1>Y</b1>를`).
- 코드는 적어도 한 번, `<xN/>`·`<mN/>`는 정확히 한 번 나와야 한다.

검증에 실패하면 재시도한다. 피드백은 무엇이 빠지거나 겹쳤는지 태그 이름으로 말한다
("<a41> is missing", "<b2> is closed inside <i1>"). 재시도 요청의 세그먼트는 처음과 같은
태그 텍스트와 번호를 쓰고, 세그먼트마다의 태그 표는 시도 사이에 그대로 유지된다. 기존
경로로 보낼지(3.1)는 첫 시도 전에 한 번 정하고 도중에 바꾸지 않는다. 한 세그먼트짜리
요청에서 `[1]` 없이 온 답을 받아 주는 지금의 판독(`parse_response_for`)은 태그 모드에서도
그대로다.

### 3.3 직렬화 정책 (CommonMark)

직렬화기는 원래 표기로 먼저 내고, pulldown-cmark로 다시 읽어 태그 구조와 글자가 의도와
같은지 본다. 다르면 강조 태그마다 아래 순서로 바꿔 보며 탐욕적으로 맞춘다.

1. 원문의 표시 그대로.
2. `_`를 `*`로 (`_arity_는` → `*arity*는`).
3. 괄호 풀이를 강조 밖으로 (`**외적**(outer product)에서`). 풀이 안에 링크나 코드가 있어도 된다.
4. 링크 하나만 감싼 강조를 링크 안으로 (`[**Fetch**](url)는`).
5. 강조 전체를 감싼 따옴표를 밖으로 (`"*권한*"은`).
6. 뒤따르는 조사를 강조 안으로 (`*… `impl Trait`의*`, `*r+로*`).
7. 최후 수단으로 HTML `<em>`·`<strong>`. 스파이크에서는 한 번도 쓰이지 않았다.

보이지 않는 문자(`&#8203;`)는 쓰지 않는다. 렌더링은 되지만 검색·복사·diff에 흔적을
남긴다. 6은 조사까지 기울여 쓰는 타이포그래피 비용이 있지만 순수 Markdown이고, 규칙만
알려 주었을 때 모델이 스스로 고른 꼴이기도 하다(robustness 7절).

그 밖의 규칙:

- 단축·축약 참조 링크의 텍스트가 바뀌면 `[텍스트][레이블]`로 쓴다. 텍스트가 같아도
  뒤에 `(`나 `[`가 바로 붙으면 전체 참조로 쓴다(`[x](GCI)`는 인라인 링크로 읽힌다).
- 이스케이프는 필요한 곳만 한다: `\`, `` ` ``, `*`, 식별자 밖의 `_`, 이어진 `~~`,
  글자·`/`·`!` 앞의 `<`, 엔티티처럼 보이는 `&`, 줄 머리에서 공백이 뒤따르는 `#`·`-`·`+`,
  줄 머리의 `>`. 대괄호는 이스케이프하지 않는다(문서에서 참조로 풀릴 수 있는 것을
  망가뜨린다).
- 표 셀(`BlockType::Table`)에서는 `|`를 `\|`로 쓴다.

### 3.4 파이프라인과 설정

- **소스별로 켠다**: `[[sources]]`에 `inline_tags = true`(기본 꺼짐). `Markup`이 아니라
  소스의 파서 이름으로 정한다(raytracing처럼 한 프로젝트에 markdeep과 markdown 소스가
  섞일 수 있다). 1단계에서는 `parser = "markdown"`에만 허용하고, 다른 파서에 켜면 설정
  오류다. 문서 안내: mdBook처럼 `$` 수식이 없는 CommonMark 렌더러에서만 켠다.
  MyST(역할 `` {ref}`…` ``의 보이는 레이블, `dollarmath`), MDX(`{…}` 표현식, JSX),
  pandoc gfm(`$` 수식 여부 미확인)은 방언별 규칙을 갖춘 1b에서 다룬다.
- **파이프라인 순서**(`translate_with_evaluation_observed`):
  1. 응답을 `[N]`으로 나누고 번호 무결성을 본다(지금과 같다. 어긋나면 배치 전체 재시도).
  2. 세그먼트마다 판독·검증한다. 태그 문제는 그 세그먼트의 재시도 사유가 되고, 피드백은
     태그 이름으로 말한다("<a41> is missing", "<b2> closes inside <i1>", 코드 문제는 3.2).
  3. 통과한 세그먼트를 직렬화한다.
  4. 정렬 검사(`alignment::misaligned`)를 **직렬화한 Markdown**에 대해 돌린다. 태그 텍스트는
     링크 목적지를 숨겨 앵커가 약해지기 때문이다. 어긋나면 지금처럼 배치 전체 재시도.
  5. 평가기를 돈다. 태그 모드에서는 서식 평가기 대신 **태그 모드 서식 검사**를 쓴다:
     (a) 직렬화 결과를 pulldown-cmark로 다시 읽어 의도한 구조와 글자가 같은지 본다
     (다르면 직렬화기 결함이다. 재시도하지 않고 경고로 남기고, 그 세그먼트의 모든 강조를
     HTML 표기로 다시 직렬화해 한 번만 다시 확인한다. 그래도 다르면 경고와 함께 그대로
     저장한다), (b) 산문 괄호 검사(`parenthesis_issues`, 두 겹·짝)는 지금처럼 재시도
     사유다. 강조 개수·제약 쌍·코드 내용·줄 머리 구문 검사는 태그 검증과 직렬화기가
     보장하므로 돌리지 않는다. 그래야 강조 분할(3.2)이나 모델이 고칠 수 없는 Markdown
     피드백(`*arity*는`)으로 재시도가 헛돌지 않는다. 용어집·어미·링크 평가기는 그대로다.
  6. `repair_markdown_emphasis`는 돌리지 않는다(직렬화기가 대신한다).
- 프롬프트: 기본 프롬프트에서 `closing_rule`(Markdown 규칙)만 태그 규칙으로 바꾼다.
  마크업 보존 문장의 코드 부분과 GFM 경고 표시 문장(AGENTS.md 규칙)은 그대로 둔다.
  커스텀 `prompt_template`을 쓰는 프로젝트는 새 자리표시자 `{inline_tags}`를 넣어야 하며,
  없는데 켜면 설정 오류로 알린다.
- 관찰: 강조마다 고른 직렬화 전략을 tracing에 남겨 롤아웃에서 재작성 비율(스파이크
  13~14%)을 볼 수 있게 한다.
- 구성 요소: 파이프라인과 평가기가 있는 `yeokja-translate`에 모듈
  `crates/translate/src/inline/`을 둔다. `markdown::tagify(segment, &DocContext) ->
  Result<Tagged, Untaggable>`, `read(reply, &Tagged) -> Result<Tree, Vec<Problem>>`, `render(&Tree, &Tagged,
  Position) -> String`. `DocContext`는 참조 정의 레이블을 담으며, orchestrator가
  `Document.source`를 pulldown-cmark로 한 번 읽어 만든다. `Position`은 세그먼트가 표 셀인지를
  알리며, orchestrator가 `translate_file`에서 쥔 `Document`의 `Block.block_type`을
  `SegmentId`로 찾아 넘긴다(`SegmentState`에는 블록 종류가 없다). 파서 crate와
  `DocumentParser`는 바꾸지 않는다.
- 관찰: 기존 경로로 보낸 요청(3.1)의 비율도 tracing에 남긴다.

### 3.5 롤아웃

1. rustc-dev-guide의 스크래치 사본(설정·용어집을 복사하고 `upstream`은 링크, `state/`는
   별도 사본이라 추적되는 state를 건드리지 않는다)에서 켜고 스파이크 표본(세 챕터)을 두 번 재번역해
   같은 표본의 지금 파이프라인과 비교한다(4절 합격 기준). 통과하면 저장소 설정에서 켠다.
2. 새로 번역되거나 다시 번역되는 세그먼트에만 적용된다. 기존 번역은 그대로다.
3. 결과가 기준을 넘으면 rust-forge·furiosa-opt·webassembly-component-docs의 mdBook
   소스로 넓힌다.

## 4. 검증

- 단위 테스트: 태그화·왕복(목록 표시처럼 보이는 세그먼트, 각주 참조, 수식, 참조
  링크, 짝 맞는 인라인 HTML, 태그화할 수 없는 세그먼트), 느슨한 판독의 각 규칙, 코드
  맞추기의 다섯 경우(이미 맞춘 코드를 뒤에서 한 번 더 바꿔 쓴 경우가 5로 떨어지는지 포함), 직렬화 정책의 각 단계, 단축 참조 규칙, 표 셀의 `|`, 태그 모드 서식
  검사(강조 분할을 결함으로 보지 않음), 파이프라인 순서(태그 문제 재시도, 직렬화 뒤 정렬
  검사, 요청 단위 기존 경로 전환).
- 말뭉치 왕복: 저장된 CommonMark 세그먼트 전체에서 렌더링 HTML 동일 99.99% 이상
  (스파이크 41,190/41,194).
- 모델 A/B(스파이크 표본, 두 번 실행, 재시도 포함한 실제 파이프라인끼리): 구조 결함 0,
  코드 뒤 조사 일치 97% 이상, 재시도율이 지금 파이프라인 이하, 그리고 **사람이 읽은
  태그 응답 100개 이상에서 엉뚱한 낱말을 감싼 태그 0**.
- rustc-dev-guide 빌드: 본문(code·pre 밖)에 글자로 남은 강조 표시 0.

## 5. 범위 밖과 이후 단계

- 1b단계: MyST(역할은 이름과 대상은 불투명하게, 보이는 레이블은 짝 태그로;
  `dollarmath`는 `<mN/>`), MDX(`{…}`와 JSX 표현식은 `<xN/>`, `{`·`}` 이스케이프), pandoc gfm.
- 2단계: RST 코덱(스파이크 S4). docutils 인라인 인식 규칙과 구두점 표를 Rust로 옮긴다.
  RST는 `\ `라는 탈출구가 늘 있어 직렬화 정책이 단순하다. 문장 분할이 인라인 마크업을
  자르지 않도록 블록 단위로 태그화한다.
- 3단계: 문단 단위 요청(스파이크 S3). 한 문장짜리 문단에는 표시를 넣지 않는다.
- AsciiDoc, LaTeX, Verso, MkDocs 코덱.
- 기존 번역 감사: 저장된 번역을 느슨하게 읽어 재직렬화하는 도구(스파이크 S2)를
  `evaluate`의 감사 모드로 붙여 깨진 번역을 찾고 고친다. 1단계와 독립이라 먼저 해도 된다.

## 6. 되짚을 수 있는 결정

- 조사를 강조 안으로 넣는 정책(3.3의 6)은 타이포그래피 판단이다. 싫다면 HTML(7)로
  바꿀 수 있지만, MyST·MDX에서 인라인 HTML이 실제로 렌더링되는지 빌드로 확인해야 한다.
- 이미지 대체 텍스트는 1단계에서 번역하지 않는다. 짝 맞는 인라인 HTML의 속성 값
  (`title="…"`)도 번역하지 않는다.
- 강조 태그의 분할(3.2)은 강조 개수를 원문과 다르게 만든다. 태그 모드 서식 검사(3.4의
  5)는 개수를 대조하지 않으므로 이를 결함으로 보지 않는다.
