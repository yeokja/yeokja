# 인라인 태그 전송 설계 (1b단계: MyST, MDX)

1단계(`2026-09-22-inline-tag-transport-design.md`)의 태그 전송을 `myst`·`mdx` 파서 소스로
넓힌다. 전송 형식, 판독 규칙, 직렬화 정책, 파이프라인 순서는 1단계 그대로이며, 이 문서는
방언마다 달라지는 것만 정한다. 대상은 nix-dev(MyST), zero-to-nix와
putting-the-you-in-cpu(MDX)다.

## 1. 조사 (2026-09-22)

세 프로젝트의 저장된 세그먼트(nix-dev 3,095, zero-to-nix 903, putting-the-you-in-cpu의
MDX 803)와 각 사이트의 렌더러 설정을 보았다.

**MyST (nix-dev).** `myst_enable_extensions = ["colon_fence", "linkify", "tasklist",
"attrs_block"]`. `dollarmath`·`amsmath`·`strikethrough`·`substitution`은 꺼져 있다.
산문의 인라인 구문 가운데 CommonMark에 없는 것은 역할뿐이다.

| 역할 | 개수 | 보이는 글자 | 지금 번역 |
|---|---|---|---|
| `` {ref}`텍스트 <label>` `` | 14 | 텍스트 | 텍스트를 번역(14/14) |
| `` {ref}`label` `` | 8 | 절 제목(Sphinx가 채움) | 그대로(8/8) |
| `` {term}`용어` `` | 39 | 용어 | 그대로 33, `` {term}`Nix 언어 <Nix language>` `` 꼴로 번역 6 |
| `` {download}`텍스트 <path>` `` | 5 | 텍스트 | 그대로(5/5) |

지금 CommonMark 코덱에 MyST 세그먼트를 넣으면 역할은 글자 `{ref}`와 코드 스팬으로
갈라진다. 모델이 앞의 `{ref}`를 빠뜨려도 막을 수 없고, 코드 내용은 엄격하게 맞추므로 보이는
레이블을 번역하면 "code is not in the source"로 재시도가 헛돈다.

**MDX (zero-to-nix, putting-the-you-in-cpu).** Astro의 `@astrojs/mdx`(micromark +
remark-gfm)다. 세그먼트 안의 MDX 고유 구문은 적다: 인라인 JSX `<Language />` 4개,
`<cite>…</cite>` 2개, 인라인 `{…}` 표현식 0개. 나머지는 CommonMark·GFM(강조, 링크,
각주 1개, 취소선 1개)이다. `@mdx-js/mdx`로 직접 확인한 문법 차이:

| 입력 | 결과 |
|---|---|
| `a < b 입니다`, `a } b` | 글자 |
| `x <3 y`, `a<b` | **컴파일 오류**(`<` 뒤가 이름으로 읽힘) |
| `\<`, `\{`, `\}` | 글자 `<`, `{`, `}` |
| `<em>기울임</em>을` | `em` 요소 |
| `www.example.com/a_b` | GFM 자동 링크 |

`<https://…>` 자동 링크와 HTML 주석은 MDX에서 쓸 수 없다(원문에도 없다).

**필드.** 두 파서는 Markdown이 보지 않는 곳의 문자열도 블록으로 내놓는다. MDX의 front
matter 값(`title:`, `description:` 등)과 JSX `title="…"` 속성, MyST의 toctree 항목 제목
(`제목 <target>`)은 컨테이너가 인용할 뿐 마크업으로 읽지 않는 문자열이다. 이것을
CommonMark 코덱에 넣으면 `2 * 3`이 `2 \* 3`으로 나가 YAML 제목에 역슬래시가 찍힌다.
MyST의 지시문 제목(`:::{note} 제목`)과 `:caption:` 값은 MyST 인라인으로 읽힌다.

## 2. 결정

### 2.1 방언

`inline::markdown`에 방언 `Dialect { CommonMark, Myst, Mdx }`를 두고 `DocContext`가
지닌다(`DocContext::new(source, dialect)`). orchestrator는 소스의 파서 이름으로 방언을
고른다(`markdown`→CommonMark, `myst`→Myst, `mdx`→Mdx). 방언마다 바뀌는 것은 넷이다.

| | CommonMark | MyST | MDX |
|---|---|---|---|
| 가리는 구문(1단계의 `mask`) | 수식 `\\(…\\)`·`\\[…\\]`, 각주 `[^x]` | + 역할 `` {name}`…` `` | + 표현식 `{…}` |
| 취소선 `~~` | 켬 | 끔(확장 꺼짐, 글자) | 켬(GFM) |
| 텍스트 이스케이프 | 공백 사이가 아닌 `~` | `~`는 하지 않음 | 공백 사이가 아닌 `~`, 모든 `{`·`<` |
| 응답의 `{name}` + 코드 | 글자 + 코드 | 역할 하나로 읽음 | 글자 + 코드 |

그 밖의 규칙(강조, 링크, 참조 정의, 짝 맞는 인라인 HTML, 표 셀의 `|`, 직렬화 전략 탐색)은
셋이 같다. micromark와 markdown-it은 pulldown-cmark와 같은 강조 규칙을 따르므로 직렬화
정책(1단계 3.3)도 그대로 쓴다. **되읽기 확인은 방언을 따른다**: 직렬화 결과를 같은 방언의
가림과 옵션으로 다시 읽고, 가린 구문은 태그와 같은 모양으로 읽는다(레이블 역할은 `(a`+레이블
글자+`)`, 글자 그대로 역할은 `r:내용|`로 코드의 `c:내용|`과 구별, 표현식은 `e`). 그렇지 않으면
역할이나 표현식이 든 세그먼트가 모두 확인 실패로 떨어져 강조가 전부 HTML 표기로 바뀐다.

GFM(pulldown-cmark와 remark-gfm)은 물결표 하나로도 취소선을 만든다. 1단계는 이어진 `~~`만
이스케이프해 원문 `\~(++)\~`가 취소선으로 바뀌었다(MDX 말뭉치 왕복이 드러냈다). 취소선을 쓰는
방언에서는 양쪽이 공백이 아닌 `~`를 모두 이스케이프한다.

### 2.2 MyST 역할

역할(`{name}` 바로 뒤의 백틱 스팬, 이름은 myst-parser와 같이 `[A-Za-z0-9_+:-]+`)은 원문에서
하나의 구문으로 가린다(수식·각주와 같은 방식). 가린 역할은 둘 중 하나가 된다.

- **레이블 역할 → `<aN>레이블</aN>`.** 링크처럼 보이는 텍스트를 번역하게 한다.
  - 명시 레이블 `` {name}`레이블 <대상>` ``(Sphinx `split_explicit_title`과 같은 규칙)이고
    `name`이 상호 참조 역할일 때: `ref`, `doc`, `term`, `numref`, `any`, `download`,
    `keyword`, `option`, `envvar`, `token`, `pep`, `rfc`, 또는 도메인 역할(`py:func`처럼
    `:`를 품은 이름).
  - `` {term}`용어` ``: 보이는 글자가 곧 대상이다. 레이블은 용어, 대상도 용어다.
  - 되돌리기: `` {name}`번역 <대상>` ``. 암시 레이블 `term`은 번역이 원래 용어와 같으면
    `` {term}`용어` ``로, 다르면 `` {term}`번역 <용어>` ``로 쓴다(지금 번역 6건이 쓴 꼴).
    레이블은 역할 안의 날것 글자라 Markdown 이스케이프를 하지 않고, 백틱이 들어가면 더 긴
    백틱 줄로 감싼다.
  - 레이블 역할 안에는 글자만 온다. 안에 다른 태그나 코드 스팬을 두면 문제다
    ("<a3> holds plain text only — move <b2> outside it").
- **글자 그대로 역할 → 코드처럼.** 그 밖의 역할(`` {ref}`label` ``처럼 Sphinx가 보이는
  글자를 채우는 것, `{kbd}`·`{code}`·`{math}` 등)은 모델에게 원문 그대로 보이고
  (`` {ref}`install-nix` ``), 1단계의 코드 규칙으로 엄격하게 맞춘다: 내용이 같은 원문
  역할(또는 되풀이)이면 원문 바이트로 되살리고, 그 밖은 문제다. 조사 판단에 내용이 보이는
  편이 낫다는 1단계 조사를 따른다. 덜어 내기(복수형·`()`)는 역할에 적용하지 않는다.
  - 응답에서 코드 스팬 바로 앞(공백 없이 붙은)의 `{name}`은 그 코드에 붙여 읽는다. 모델이 `{ref}`를
    빠뜨리든 남기든 원문 바이트로 되살리므로 결과가 같다. 앞말이 붙은 스팬은 원문 역할에,
    맨 스팬은 원문 코드에 먼저 맞춘다(같은 내용의 코드와 역할이 뒤바뀌지 않게).
  - 코드 맞추기의 4번(원문이 평문으로 쓴 말을 코드로 씀)은 역할이 보이는 글자도 평문으로 본다.
    `` {term}`Nixpkgs` ``를 번역하며 한국어가 주어를 되풀이해 `` `Nixpkgs` ``라고 쓰면 원문에 없는
    코드라는 문제로 재시도가 헛돌기 때문이다(`{term}` 39개 중 33개가 제품 이름 한 낱말이다).
  - myst-parser는 역할 이름을 36자까지, 내용이 백틱으로 시작하거나 끝나지 않을 때만 읽는다.
    번역한 레이블이 백틱으로 끝나는 경우는 다루지 않는다(드물다).

프롬프트는 바꾸지 않는다. 글자 그대로 역할은 백틱 스팬이라 "copy every code span exactly"
규칙에 들고, 레이블 역할은 `<aN>` 규칙에 든다.

### 2.3 MDX 표현식과 JSX

- 표현식 `{…}`는 가려서 `<xN/>`로 준다. 여는 `{`에서 괄호 깊이가 맞는 `}`까지다(말뭉치에
  인라인 표현식이 없어 JS 문자열·주석은 따지지 않는다). 역슬래시로 이스케이프한 `\{`는
  글자다. 짝이 없으면 태그화할 수 없는 세그먼트다(요청을 기존 경로로).
- 인라인 JSX는 표현식을 가린 뒤 pulldown-cmark가 인라인 HTML로 읽으므로 CommonMark와
  같다: 세그먼트 안에서 짝을 이루면 `<hN>…</hN>`(`<cite>…</cite>`), 아니면 `<xN/>`
  (`<Language />`).
- 텍스트 이스케이프: `{`와 `<`는 늘 `\{`, `\<`. `<`는 뒤가 공백이면 글자지만 텍스트 조각
  끝의 `<` 뒤에 무엇이 올지(태그, 코드)는 조각 안에서 알 수 없으므로 가리지 않는다. `}`는 글자로
  읽히므로 두지 않는다.
- 최후 수단 HTML 표기(`<em>`)는 MDX에서 JSX 요소로 렌더링된다.

### 2.4 필드: 글자 그대로의 문자열

- 모델 `BlockRole`에 `Literal`을 더한다: "컨테이너가 인용할 뿐 마크업으로 읽지 않는 문자열
  (front matter 값, JSX 속성, toctree 항목 제목)". 방언 공통부의 `Extra`에 `literal: bool`을
  두어 `push_extra`가 역할을 적는다. MDX 파서의 필드는 모두, MyST 파서는 toctree의 항목
  제목과 `:caption:`이 `literal`이다(Sphinx가 사이드바 글자로 그대로 쓴다). 지시문 제목과
  코드 블록의 `:caption:`은 MyST 인라인이므로 아니다. mkdocs·markdeep과 HTML 블록 안 산문은
  바꾸지 않는다(`false`).
- 블록 종류보다 역할이 먼저다: `Literal` 블록은 표 안에 있어도 `Plain`이다.
- orchestrator는 `BlockRole::Literal` 블록의 세그먼트에 `Position::Plain`을 준다. 태그화는
  글자만 이스케이프(`&<>`)하고 태그를 만들지 않는다. 판독은 태그를 버리고 백틱도 글자로
  둔다(코드 맞추기 없음). 직렬화는 Markdown 이스케이프 없이 글자 그대로 내고 되읽기 확인을
  하지 않는다. 컨테이너의 인용 이스케이프는 지금처럼 파서의 재구성이 맡는다.
- 이렇게 해야 문서 첫 요청(front matter 제목이 든)이 통째로 기존 경로로 가지 않는다.

### 2.5 설정과 연결

- `inline_tags = true`를 `markdown`·`myst`·`mdx` 파서에 허용한다. 그 밖의 파서는 여전히
  설정 오류다. `inline_tags_for`도 같다(`evaluate`·서버가 이것으로 태그 모드 서식 검사를
  고른다).
- 파이프라인·프롬프트·평가기는 바꾸지 않는다. 방언은 `InlineBatch.ctx`로, 판독에는
  `Tagged.dialect`로 흐른다.
- 켠 소스는 `yeokja evaluate`와 서버에서도 태그 모드 서식 검사를 쓴다(1단계와 같다). 그래서
  켜기 전에 지금 방식으로 번역된 nix-dev 3,095개도 역할의 리터럴화 검사(`evaluator_format.rs`의
  역할 검사) 대신 괄호 검사만 받는다. 1단계가 rustc-dev-guide에서 받아들인 것과 같은 절충이다.
- `dollarmath`를 켠 MyST 프로젝트나 `$` 수식을 쓰는 MDX 프로젝트(remark-math)는 아직
  없다. 그런 프로젝트에 켜려면 수식 가림을 방언에 더해야 한다. 체크리스트에 적는다.

## 3. 검증

- 단위 테스트: 방언별 태그화(레이블 역할·글자 그대로 역할·표현식·`<Language />`·
  `<cite>` 짝·MyST의 `~~` 글자), 역할 판독(`{name}` 빠뜨림·남김, 코드와 역할이 같은 내용일 때
  짝짓기, 레이블 역할 안의 태그는 문제), 직렬화(암시 `term` 레이블, 명시 레이블, MDX `{`·`<`
  이스케이프), `Position::Plain` 왕복, 설정 허용 범위, orchestrator가 방언과 `Plain`을 고름.
- 말뭉치 왕복: 저장된 `myst`·`mdx` 세그먼트 전체를 태그화→그대로 판독→직렬화해 원문과
  렌더링이 같은지 본다(pulldown-cmark HTML 비교를 방언의 옵션으로, 가린 구문은 바이트로
  되살아나므로 비교가 유효하다). 기준 99.99% 이상. 바이트가 달라진 결과는 방언 렌더러로도
  확인한다: MyST는 markdown-it-py(myst-parser 설정), MDX는 micromark(mdx·gfm)로 토큰·트리를
  비교한다.
- 모델 A/B(스크래치 사본, 추적되는 state는 건드리지 않음): nix-dev에서 역할·링크·강조가
  많은 챕터로 약 300개, zero-to-nix·putting-the-you-in-cpu에서 합쳐 약 300개를 태그 모드 두
  번, 지금 방식 한 번 번역한다. 채점은 방언 렌더러로 한다(MyST는 markdown-it-py 토큰, MDX는
  컴파일 성공과 mdast): 구조 결함(강조·링크·역할·코드·JSX·표현식 손실, 글자로 남은
  `*`·`_`, MDX 컴파일 오류), 코드·역할 뒤 조사 일치, 재시도율, 기존 경로 비율.
  합격 기준은 1단계 4절과 같다: 구조 결함 0, 조사 일치 97% 이상, 재시도율이 지금 방식 이하,
  사람이 읽은 태그 응답 100개 이상(두 방언 합)에서 엉뚱한 낱말을 감싼 태그 0.
- 사이트 빌드: 합격 뒤 켠 세 프로젝트를 스크래치 번역 결과로 한 번 빌드해 본문에 글자로
  남은 강조 표시, 깨진 역할(Sphinx 경고 `undefined label`·`term not in glossary`의 증가),
  MDX 컴파일 오류가 없는지 본다.

## 3.1 결과 (2026-09-22)

- 설계 검토(Fable, APPROVE WITH CHANGES)의 요구를 반영했다: 방언을 따르는 되읽기 확인과
  구별되는 모양, 역할 글자를 `written_as_text`에, toctree `:caption:`도 `Literal`, MDX `<`·`{`
  전부 이스케이프, 왕복 비교의 방언 옵션, 표현식 가림 단순화.
- 말뭉치 왕복: MyST 3,095개 모두 태그화되어 3,095/3,095, MDX 1,706개 가운데 1,692개가
  1,692/1,692(14개는 문장 분할이 여러 문장짜리 기울임을 자른 것으로 기존 경로), CommonMark는
  1단계 그대로 36,556/36,556. 바이트가 달라진 결과(MyST 5, MDX 28)는 markdown-it-py와 micromark
  에서도 원문과 구조가 모두 같았다. 왕복이 드러낸 한 글자 취소선 결함(2.1)은 1단계
  코덱에도 있던 것이다.

## 4. 롤아웃

1. 위 검증을 넘으면 세 프로젝트의 `myst`·`mdx` 소스에 `inline_tags = true`를 켠다.
   putting-the-you-in-cpu의 `ui/*.md`(`markdown` 파서, 사이트 UI 문자열)는 mdBook이 아니라
   스크립트가 읽는 문자열이라 켜지 않는다.
2. 새로 번역되거나 다시 번역되는 세그먼트에만 적용된다. 기존 번역은 그대로다.

## 5. 되짚을 수 있는 결정

- 암시 `term`을 레이블 역할로 본 것: 지금은 33/39가 영어 용어를 그대로 두었다. 태그 모드에서
  모델이 용어를 번역하면 `` {term}`Nix 언어 <Nix language>` ``가 된다. nix-dev의 한국어 용어
  줄 패치(`patches/glossary-korean-terms.patch`)와 충돌하지 않는다(명시 대상은 원래 용어를
  가리킨다). 영어로 남기고 싶다면 용어집이 정한다.
- 글자 그대로 역할을 `<xN/>`로 숨기지 않은 것: `` {ref}`install-nix` ``의 보이는 글자는 절
  제목이라 모델이 어느 쪽이든 모르지만, 내용이 보이면 문장을 짜기가 낫고 1단계의 코드 규칙과
  같아진다.
- MDX `}`를 이스케이프하지 않는 것: 컴파일러가 글자로 읽음을 확인했다.
