# 한국어 번역 eval 설계

yeokja 번역 프로젝트를 새 모델로 다시 번역할지 판단하기 위한 고정 평가
세트입니다. 첫 질문은 "현재 쓰는 `claude-sonnet-5`에 비해 `claude-opus-5-5`나
`claude-fable-5-1`이 한국어 기술 문서 번역을 눈에 띄게 잘하는가, 특히
번역투(Claudish)가 줄었는가"입니다.

## 1. 원칙

- **운영 경로를 그대로 재생한다.** 항목은 yeokja가 실제로 모델에 보내는
  `TranslateRequest`(`crates/translate/src/provider.rs`)를 재현할 수 있어야
  합니다. 프롬프트를 따로 만들면 운영에서 볼 결과와 다른 것을 재게 됩니다.
- **데이터셋은 커밋해서 고정한다.** 추출 도구는 한 번 쓰는 생성기이고, 결과는
  `v1/`에 동결합니다. 원문 서브모듈이 움직여도 세트는 바뀌지 않습니다. 고칠
  일이 생기면 `v1`을 고치지 않고 `v2`를 만듭니다.
- **라이선스는 파일 단위로 나눈다.** 발췌는 `state/`가 커밋된(이미 원문을
  배포하고 있는) 프로젝트에서만 뽑고, 원문
  라이선스가 같은 항목끼리 한 파일에 모아 그 파일에 라이선스를 붙입니다
  (루트 [`LICENSE.md`](../../LICENSE.md) 참조).
- **후보 모델은 채점하지 않는다.** 후보가 모두 Anthropic 모델이므로 채점은
  다른 회사 모델과 사람이 맡습니다.

## 2. 파일 구성

```
evals/ko-translation/
  README.md                        이 문서
  v1/
    MANIFEST.md                    파일별 라이선스·저작자·원문 커밋·추출 명령·오염 고지
    glossaries/<project>.toml      추출 시점의 프로젝트 용어집 사본
    items.permissive.jsonl         MIT, Apache-2.0, BSD-3-Clause, CC0-1.0, 퍼블릭 도메인
    items.cc-by-4.0.jsonl
    items.cc-by-sa-3.0.jsonl       hott
    items.cc-by-sa-4.0.jsonl
    items.cc-by-nc-sa-4.0.jsonl    zero-to-nix
    synthetic.jsonl                직접 작성한 항목 (MIT OR Apache-2.0)
  runs/<YYYY-MM-DD>-<label>/
    run.toml                       후보 모델, 프로바이더 설정, yeokja 커밋, 프롬프트 해시
    outputs.<license>.jsonl        입력 파일과 같은 라이선스 단위로 저장
    gates.jsonl                    자동 검사 결과 (번역문을 담지 않음)
  judgments/<YYYY-MM-DD>-<label>/
    pairs.jsonl                    쌍대 비교 판정 (채점자별)
    human.jsonl                    사람 판정
  reports/<YYYY-MM-DD>-<label>.md  요약 보고서
```

napkin은 뽑지 않습니다. 본문은 CC BY-SA 4.0이지만 세그먼트가 GPL-3.0인 LaTeX
소스에서 나오기 때문입니다. peps는 번역 대상인 퍼블릭 도메인/CC0 PEP만 쓰고 Open
Publication License PEP는 뺍니다. 프로젝트별 라이선스와 범위는 `v1/sources.toml`에
있습니다. 모델 출력은
원문의 2차적 저작물이므로 입력과 같은 라이선스 파일 단위를 따릅니다.

## 3. 항목 형식

한 줄이 **운영 요청 하나**입니다. 대부분의 프로젝트가 `batch_segments = 24~32`로
여러 블록을 한 요청에 묶으므로, 블록을 따로 떼어 보내면 운영과 다른 조건(더 짧은
문맥, 문장 간 내용 이동이 일어날 여지가 적음)을 재게 됩니다. 그래서 요청은
프로젝트 설정의 묶음 규칙 그대로 만들고, **채점 단위는 그 안의 블록**으로 합니다.

요청은 orchestrator가 실제로 만드는 `TranslateRequest`와 인라인 태그 정보
(`InlineBatch`)를 그대로 직렬화해 둡니다. 실행 때 원문 서브모듈이나 파서가
필요 없고, 추출 시점의 yeokja가 보냈을 요청이 바이트 단위로 재생됩니다.

```json
{
  "id": "rustc-dev-guide/src/overview.md#3",
  "kind": "real",
  "project": "rustc-dev-guide",
  "source_path": "upstream/src/overview.md",
  "upstream": "https://github.com/rust-lang/rustc-dev-guide@<commit>",
  "license": "MIT OR Apache-2.0",
  "attribution": "The Rust Project Developers",
  "yeokja_commit": "<추출 시점 커밋>",
  "request": { "segments": [], "block_context": "", "markup": "Markdown", "inline_tags": true, "…": "…" },
  "inline": { "tagged": {}, "ctx": {} },
  "blocks": [
    {"id": "section:5/block:1", "raw": "…블록 원문…", "strata": ["prose", "inline-markup"], "probes": [],
     "segments": [{"id": "section:5/block:1/seg:0", "index": 1, "source": "…", "reference": null, "known_bad": null}]}
  ],
  "glossary": "glossaries/rustc-dev-guide.toml"
}
```

- 용어집은 운영처럼 전체를 보냅니다. `request`에 이미 들어 있고, 사람이 읽기
  좋게 `glossaries/`에도 사본을 둡니다.
- `blocks[].source`는 채점자와 사람이 읽는 원문이고, `request`는 모델이 받는
  형태(인라인 태그 텍스트일 수 있음)입니다.
- `reference`/`known_bad`는 사람이 고친 정답이 있는 세그먼트에만 둡니다(4.3절).
- 실행기는 `yeokja_commit`과 다른 yeokja로 돌리면 경고합니다. 태그 형식이 바뀌면
  새 버전의 세트를 만듭니다.

## 4. 표본 구성

### 4.1 실제 항목 (약 60요청)

프로젝트 설정대로 만든 모든 요청 가운데 고정 시드로 뽑습니다. 요청 하나에 블록이
수십 개 들어 있으므로 60요청이면 블록은 수백 개가 됩니다.

- **층화:** 프로젝트마다 먼저 2요청씩, 그다음 목표 수까지 돌아가며 채우되
  프로젝트당 최대 4요청, 파일당 1요청. 파일 안에서는 운영에서 흔한 8세그먼트
  이상 요청을 우선합니다. 파서 분포는 `MANIFEST.md`에 기록합니다.
- **제외:** 모든 세그먼트가 20자 미만이거나 코드·URL을 뺀 글자가 12자 미만인 요청.
- **판정용 블록 표본:** 쌍대 채점은 비용 때문에 이 중 약 150블록만 합니다.
  인라인 마크업이 많은 블록, 긴 블록, 수식이 섞인 블록이 3분의 1 이상 되게
  고정 시드로 뽑습니다. 자동 관문은 모든 블록에 돌립니다.

### 4.2 합성 항목 (약 50개)

과거에 실제로 깨졌던 유형을 직접 쓴 짧은 문단으로 재현합니다. 원문 변화와
무관하고 라이선스 제약이 없습니다. `v1/synthetic/`에 작은 yeokja 프로젝트로 두고
실제 항목과 같은 방식으로 요청을 만듭니다. 모든 블록을 판정 표본에 넣습니다.

| 유형 | 예 |
|---|---|
| 참조 링크 | `[text][ref]`, 줄임 참조 `[ref]`, 문장을 넘는 굵게 안의 참조 |
| GFM 경고 | `> [!NOTE]` 뒤 여러 줄 본문, 마커만 있는 줄 |
| 수식 | 인라인 수식 사이의 문장, 수식 안 `\text{}` |
| 긴 블록 | 5문장 이상, 잘림과 문장 간 내용 이동 유발 |
| 용어집 충돌 | 용어집 용어가 코드 식별자와 겹치는 문장 |
| 번역투 유발 | 영어식 명사구, 수동태 연쇄, "you" 주어 문장, 줄표 삽입구 |

각 합성 항목에는 무엇을 시험하는지 `probe` 필드로 적습니다.

### 4.3 정답이 있는 어려운 항목 (약 15블록)

인라인 마크업 감사에서 사람이 고친 세그먼트입니다(`b1d50b9`, `f1c6c2c`,
`ca36ead`). 잘못된 번역과 고친 번역이 git에 남아 있으므로 `reference`에 고친
번역을, `known_bad`에 원래 잘못된 번역을 둡니다. 그 세그먼트가 든 운영 요청을
통째로 항목으로 넣습니다. 잘린 번역을 다시 번역한 두
사례(`external-repos.md`, `rustdoc-internals.md`)가 여기에 들어갑니다.

## 5. 실행

- **후보:** `claude-sonnet-5`(현재 기준선), `claude-opus-5-5`,
  `claude-fable-5-1`. 모두 운영과 같은 `claude_code` 프로바이더로 부릅니다.
  참고용으로 `gpt-6-astra`(`codex`)를 한 번 함께 돌립니다.
- **기준선도 새로 돌린다.** state에는 번역한 모델이 기록되지 않고, 일부는 사람이
  고쳤습니다. 그래서 기존 state 번역을 Sonnet 5의 출력으로 간주하지 않습니다.
- **실행기:** CLI에 임의 세그먼트를 번역하는 명령이 없으므로, `create_provider`와
  `translate_with_evaluation_inline`/`translate_with_evaluation`
  (`crates/translate/src/pipeline.rs`)을 직접 부르는 별도 바이너리
  `yeokja-eval`(`crates/eval`)을 만듭니다. 구현 순서는
  `docs/superpowers/plans/2026-09-23-ko-translation-eval.md`에 있습니다.
- **두 결과를 모두 저장한다.** 첫 시도 출력(모델 자체 실력)과 재시도 루프를
  거친 최종 출력(운영 결과), 재시도 횟수를 함께 남깁니다. 평가기는 대부분의
  프로젝트 설정과 같이 기계 평가기만 쓰고 style 평가는 끕니다.
- **반복:** 항목마다 후보별로 한 번 돌립니다. 비결정성을 가늠하기 위해 무작위
  10요청은 세 번 돌려 편차를 봅니다.
- `run.toml`에 모델 ID, 프로바이더 설정, yeokja 커밋, 프롬프트 해시, 날짜를
  기록합니다.

## 6. 채점

### 6.1 자동 관문

사람이나 모델 판단 없이 통과·실패를 정합니다. 기존 평가기를 그대로 씁니다.

| 검사 | 구현 |
|---|---|
| 인라인 마크업 보존 | `inline::audit::audit` → `Sound`만 통과, `Repaired`는 따로 집계 |
| 링크 | `LinkEvaluator` |
| 서식·괄호 | `FormatEvaluator` / `ParenthesisEvaluator` |
| 용어집 | `GlossaryEvaluator` |
| 합쇼체 어미 | `EndingEvaluator` |
| 문장 간 내용 이동 | `alignment::misaligned` |
| GFM 경고 마커 | 마커가 원문 줄 그대로, 제 줄에 홀로 있는지 |
| 잘림 (신규) | 세그먼트 번역 길이 비율과 문장 수가 원문 대비 기준 밖이면 실패 |

잘림 검사는 지금 yeokja에 없으므로 이 eval에서 새로 만듭니다. 기준은 저장된
번역의 (번역 글자 수 / 원문 글자 수) 분포의 0.01 백분위(`v1/truncation.toml`의
`min_ratio`)입니다. 짧은 제목이나 문장은 한국어로 옮기면 비율이 자연히 낮아지므로
기준을 분포의 가장 아래쪽에 둡니다.

### 6.2 쌍대 비교

자동 관문을 통과한 출력끼리 기준선 대 후보로 비교합니다.

- **익명화:** 모델 이름을 지우고 A/B 순서를 무작위로 정합니다. 같은 쌍을 순서를
  바꿔 두 번 묻고, 두 판정이 엇갈리면 무승부로 둡니다.
- **채점자:** `gpt-6-astra`(`codex`)와 Gemini(`gemini` 프로바이더). 후보와
  같은 회사 모델은 채점에 쓰지 않습니다. 비용 때문에 Gemini는 Flash 계열을
  씁니다. 실행 시점에 Gemini API의 모델 목록에서 가장 최신의 안정판 Flash
  모델을 골라 `judges.toml`에 ID를 기록합니다. Flash는 Pro보다 판단이 거칠 수
  있으므로 7절의 방법으로 신뢰도를 확인합니다.
- **학습 비허용:** 번역과 같은 조건을 채점에도 적용합니다. Gemini는 무료
  등급에서 입력을 제품 개선에 쓸 수 있으므로 **유료(결제 연결) 등급 키만**
  씁니다.
- **항목별 판정:** 채점자는 정확성, 자연스러움, 번역투를 각각 A/B/동점으로
  고르고, 마지막에 종합 판정을 냅니다. 판정마다 한 줄 근거를 남깁니다.

### 6.3 번역투(Claudish) 기준

채점자와 사람에게 같은 목록을 줍니다.

- 영어 어순을 따른 긴 관형절, "~하는 것은 ~이다" 구문 남발
- 불필요한 피동("~되어진다", "~에 의해 ~된다")
- "당신", "여러분"처럼 원문의 "you"를 그대로 옮긴 주어
- 영어식 줄표(—)와 괄호 삽입구의 과다 사용
- "매우", "정말로", "효과적으로" 같은 원문에 없는 수식어
- 명사 나열식 제목·목록을 문장처럼 풀어 쓴 번역, 또는 그 반대
- 같은 문단 안에서 어미·용어가 흔들리는 것

### 6.4 사람 판정 (선택)

사용자가 원할 때 쌍대 비교 표본 중 30쌍을 같은 양식으로 판정합니다. 판정한
쌍이 20개 이상일 때만 채점자 신뢰도의 근거로 씁니다(7절).

- 판정 페이지는 claude.ai Artifact(비공개)이고, 판정은 페이지의 데이터베이스에
  저장합니다. `yeokja-eval human-pairs`가 쌍을, `import-human`이 판정을 다룹니다.
- 한 화면에 원문과 번역 A·B를 나란히 보여 주고, 마크업은 렌더링과 원문을 전환해
  볼 수 있습니다. 정확성, 자연스러움, 번역투, 종합을 각각 A/B/동점으로 고릅니다.
- 페이지에는 모델 이름이 없습니다. A/B와 모델의 대응표는
  `judgments/<run>/blind-map.jsonl`에만 둡니다.
- 사람의 판정 내용(`human.jsonl`)과 페이지용 쌍(`page-pairs.json`)은 커밋하지
  않습니다. 보고서에는 채점자와의 일치율만 적습니다.

### 6.5 비밀 값

API 키는 대화, 저장소, 설정 파일 어디에도 적지 않습니다. 사용자가 macOS
키체인에 한 번 저장해 두고,

```sh
security add-generic-password -s yeokja-gemini -a "$USER" -w   # 키를 묻는 프롬프트가 뜸
```

실행 스크립트가 실행할 때만 환경 변수로 꺼내 씁니다. 채점자 설정은
`api_key_env = "GEMINI_API_KEY"`로 둡니다.

```sh
GEMINI_API_KEY="$(security find-generic-password -s yeokja-gemini -w)" <실행 명령>
```

## 7. 판정 기준

실행 전에 정해 두고 결과를 보고 바꾸지 않습니다. 후보가 기준선을 대체하려면
다음을 모두 만족해야 합니다.

1. 자동 관문 통과율이 기준선보다 낮지 않다(첫 시도 기준과 최종 기준 모두).
2. 믿을 만한 채점자의 종합 판정에서 기준선 대비 승률(무승부 제외)의 95% 신뢰
   구간 하한이 50%를 넘는다.
3. 번역투 항목 승률은 따로 보고한다. "Claudish가 줄었다"는 주장은 이 수치로만
   한다.

채점자를 믿을 만한지는 다음 순서로 정합니다.

- 사람 판정이 20쌍 이상이면, 사람과의 종합 판정 일치율이 70% 이상인 채점자만
  믿습니다. 이때 사람 판정의 승률도 50%를 넘어야 "기준선을 대체할 근거가 있음"이
  됩니다.
- 그보다 적으면, 두 채점자의 종합 판정 일치율이 70% 이상일 때 두 채점자를
  믿습니다. 이때 결론은 "LLM 채점자 기준으로 우세 (사람 검증 없음)"로만
  표시합니다. 두 채점자에 공통된 취향은 이 방법으로 걸러지지 않습니다.

후보 둘이 모두 기준을 넘으면 승률, 재시도 횟수, 비용과 시간을 함께 비교해서
고릅니다. 재번역 여부는 프로젝트마다 따로 정할 수 있도록 결과를 프로젝트와
파서별로도 나눠 보고합니다.

## 8. 알려진 한계

- **오염:** 이 세트와 원문은 공개 저장소에 있으므로 이후 모델의 학습 데이터에
  들어갈 수 있습니다. 새 버전을 만들 때 합성 항목 비중을 늘려 대응합니다.
- **문맥 범위:** 운영처럼 블록 문맥만 주므로, 문서 전체 일관성(장 사이 용어
  통일 등)은 재지 못합니다.
- **용어집 검사 오탐:** 운영 용어집 검사가 "in the future"를 용어
  `future`(퓨처)로 보고 실패로 잡습니다. 모든 후보에 똑같이 걸리므로 비교에는
  영향이 없습니다.
- **표본 크기:** 판정 블록 약 225개로는 작은 차이를 구분하기 어렵습니다. 승률
  차이가 신뢰 구간 안에 있으면 "차이 없음"으로 보고합니다.
